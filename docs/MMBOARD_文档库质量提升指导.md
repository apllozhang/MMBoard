# MMBoard 文档库质量提升指导

> 适用范围：MMBoard `docs/` 文档库及其配图  
> 功能代码基线：`7e55f94`  
> 目标：将文档库建设为新维护者可以独立学习、操作、排障和验证的教程级资料  
> 说明：本文是文档质量指导，不改变已完成的功能代码验收结论。

## 可直接转发的总体意见

请把 MMBoard 文档库从“验收材料的汇总”提升为“新维护者可以独立学习、操作、排障和验证的教程”。文档应以生产功能版本 `7e55f94` 的实际行为为准：每个关键结论都能追溯到代码、配置、运行证据或验收记录；每项操作都写清前提、步骤、预期结果、异常处理和恢复办法；每张图都与正文及实现一致。已知限制、未完成事项和补录历史必须明确标识。请先修正本次评审发现的字段层级、部署演练时点等事实偏差，再按统一规范完善全库，最后请一位未参与开发的维护者依文档完成部署、备份恢复和故障排查演练。

## 二、文档的目标与读者

| 读者 | 读完后应能做到 |
|---|---|
| 产品与项目人员 | 理解系统解决的问题、能力边界、验收结果和未决事项。 |
| 新研发人员 | 理解架构、数据、接口和关键算法，能安全修改与验证。 |
| 部署与运维人员 | 能独立发布、核验、回滚、备份、恢复和排障。 |
| 管理员 | 能完成日常操作，识别结果不完整、模拟数据和错误提示。 |

**教程级文档的判据是可复现性。** 一名具备相应岗位基础知识、但不了解本项目的人，应能按照文档完成任务，并判断自己是否做对。

## 三、全库统一的事实口径

1. **版本分层：**每份文档标明适用的功能代码版本；文档修订另记日期或文档版本。当前功能基线为 `7e55f94`。纯文档提交不得写成生产功能版本。
2. **建成状态：**正文陈述已经实现和验证的行为。建议、计划、待办和补录历史分别标识，避免读者误认其已执行。
3. **证据来源：**系统行为依据代码与运行证据；历史决策依据验收和裁定记录。文档之间冲突时先核实事实，再同步修订。
4. **术语统一：**术语、状态名、字段名、错误码与《术语表》和实际接口一致；同一概念全文使用同一名称。
5. **限制如实：**单实例、无自动监控、凭据轮换待办等限制应出现在相关操作场景，而非只集中在“已知限制”一节。

## 四、每篇成文文档的推荐结构

不必机械填满所有章节，但每篇文档应回答读者的目标、实际机制、操作方法、验证方法及失败后的处理方式。

```markdown
# 标题

> 文档状态：成文 / 骨架 / 已归档
> 适用功能版本：7e55f94
> 最近核对日期：YYYY-MM-DD
> 维护责任人：角色或姓名
> 事实依据：具体代码、配置、运行记录或验收档案

## 本文解决什么问题
目标读者、使用场景、阅读前提和完成目标。

## 系统当前如何工作
整体概念、关键组成、数据流和边界。

## 操作或实现细节
准确步骤、参数、字段、示例及必要图示。

## 如何验证
检查方法、预期输出及失败时的判断方法。

## 异常与恢复
现象、可能原因、诊断顺序、恢复动作和升级条件。

## 已知限制与待办
区分已接受的限制、未完成的移交事项与未来迭代建议。

## 依据与关联文档
链接具体文件或章节，不只写“详见代码”。
```

骨架文档可以保留章节和素材指引，但须明确标为“尚不可作为操作依据”；总索引的阅读路径也应反映这一状态。

## 五、操作教程的写法

部署、备份、恢复、凭据轮换和故障处理应统一写明：

| 要素 | 必须说明 |
|---|---|
| 前提 | 所需权限、环境、工具、服务状态，以及备份或回滚准备。 |
| 步骤 | 在哪台机器、哪个目录执行什么命令；参数从哪里取得。 |
| 预期 | 成功时能看到的状态、响应或日志。 |
| 验证 | 独立的检查动作，不能只以命令退出码判断成功。 |
| 失败处理 | 从哪条日志查起、何时停止操作、如何恢复。 |
| 影响范围 | 是否中断服务、是否修改数据、能否回退。 |

命令示例应可理解。`<生产数据卷>` 等占位符须解释查询方法。生产演练必须准确说明切换时点、可能短暂运行的版本，以及演练完成后的版本核验方法。

技术设计宜按“**问题 → 机制 → 代码位置 → 可观察结果 → 限制**”展开。例如解释 `runId` 时，先说明重跑与旧任务的冲突，再说明校验机制、实现位置、复核方法和单实例边界。

## 六、接口、数据与图示的精度要求

### 接口文档

每个端点记录方法与路径、鉴权及 CSRF、请求字段的必填性和类型、成功响应、主要错误码、调用副作用及前端调用位置。示例使用真实字段层级。调整路由时，同步更新接口表和示例。

### 数据文档

每个持久化文件至少提供一个脱敏、结构真实的 JSON 示例。明确顶层与嵌套字段、可空值、单位、时间基准、读写模块、恢复策略和旧数据兼容规则。

### 图示

每张图应帮助读者回答具体问题。节点名称、顺序和分支须与正文及代码一致。修改时同时提交 `.drawio` 源文件与 SVG，检查 Markdown 引用和 `diagrams/README.md` 登记；关键事实不能只存在于图中。

## 七、变更时的维护流程

1. 从路由、数据文件、部署步骤和用户流程反查受影响文档。
2. 用代码位置、配置、测试或运行输出核对关键陈述；历史事实附裁定来源。
3. 同步修改正文、示例、图源、SVG、索引和交叉引用。
4. 检查文件、链接、图片、章节锚点、表格和代码块是否可读。
5. 检查敏感信息：只保留字段名及脱敏示例，不写入真实口令、令牌、密钥或会话值。
6. 请未参与撰写的目标读者照文档完成一项真实任务，记录必须猜测或求助之处并修订。
7. 记录修改原因、适用功能版本、核对依据和修改人。

建议在总索引增加“最后核对日期、适用功能版本、状态、维护责任人”四列，让过期文档和骨架一目了然。

## 八、最终质量门槛

- **真实：**关键描述与生产版本代码、配置和运行证据一致。
- **完整：**新人能沿索引找到概念、操作、验证、排障、恢复和移交资料。
- **可执行：**关键操作具备前提、步骤、预期结果和失败恢复。
- **可追溯：**重要结论能定位具体依据；版本与历史决策不混用。
- **一致：**术语、字段、图示、示例和交叉引用相互吻合。
- **可维护：**功能变更时知道更新哪些文件，过期状态能够被发现。
- **安全：**无凭据值，敏感操作及生产影响表述准确。

建议先完成上述 P1 事实修正，再完善部署与运维教程，最后由新维护者进行一次“冷读演练”。演练中每一次必须猜测或求助的地方，都应进入下一轮文档修改清单。
